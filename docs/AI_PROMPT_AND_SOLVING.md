# Agent Harness 自研手记：架构思考、核心设计与 AI 协同落地

本文记录我从零搭建轻量级、生产级 Agent Harness（基于 ReAct 范式）的全过程。

整个研发过程中，我采用 **双 AI 协同开发** 策略：前期由 **DeepSeek** 负责基础逻辑与原型代码的快速生成；后期演进、架构解耦、复杂自愈与核心系统联调则由 **Gemini** 介入指导与加固。

---

## 一、 核心架构思想：以确定性对抗非确定性

在设计之初，我就明确了一个核心认知：**LLM 是一个存在随机性与幻觉概率的概率计算单元，而 Harness（调度底盘）必须是具备确定性拦截、防御与状态管理的坚固管道。**

### 1. 结构化“双轨记忆”架构（Working Memory vs. Episodic Memory）

传统 Agent 最容易遇到的致命缺陷是：多轮对话后，历史消息滑动截断导致状态被遗忘；或者全部塞进对话流，消耗大量无意义的上下文并破坏前缀缓存。

为此，我设计了**双轨记忆机制**：

* **情景记忆（Episodic Memory / 线性上下文）**：纯粹的多轮对话与 Observation 流，受 `max_messages` 约束，采用 **Head-Tail 安全截断压缩**（锁定最初目标，折叠中间废话，保留最新动态）。
* **工作记忆（Working Memory / 确定性状态）**：类似业务看板（如 `todos`），在底层独立持久化在各自的 Session 实例中。每轮 ReAct 调度前，由系统动态编译并前置挂载进 System Prompt 头部。

> **收益**：状态永远驻留在系统层顶端，即使对话进行 100 轮、中间细节全被压缩折叠，待办与业务状态也绝对不会漂移或遗忘。

```
                    ┌─────────────────────────┐
                    │      System Prompt      │
                    │ ┌─────────────────────┐ │
                    │ │ 1. 工具 JSON Schema │ │  <-- 常驻顶端，锁定 Prefix Cache
                    │ ├─────────────────────┤ │
                    │ │ 2. Working Memory   │ │  <-- 动态挂载（todos 看板，确定性持久化）
                    │ └─────────────────────┘ │
                    └───────────┬─────────────┘
                                │
                    ┌───────────▼─────────────┐
                    │     Episodic Memory     │
                    │  (Head-Tail 压缩对话流)  │  <-- m0, m1 ... [折叠占位] ... m29
                    └─────────────────────────┘

```

### 2. 强类型系统级提示词协议（Contract Definition）

```text
你是一个具备工具调用能力的自主 Agent 助手，只能通过下方提供的工具获取信息或执行操作。
工具清单（JSON Schema）：[...]
当前持有的业务状态（Working Memory）：[...]

每轮只输出一个动作，且必须输出合法的单行 JSON（可先输出 <thinking>...</thinking> 展现思维过程）：
调用工具：{"action":"tool","tool":"<工具名>","arguments":{...}}
最终回答：{"action":"answer","answer":"面向用户的回复内容"}
规则：缺少信息或需要记录时果断调用工具；信息充足时直接给出 answer；不要反问用户。

```

通过将 `<thinking>` 标签剥离并单独存入可观测 Trace，既保留了大模型的思维链（CoT），又杜绝了自由文本污染下游反序列化的隐患。

## 二、 关键工程突破与踩坑演进

在开发与实机验证过程中，我舍弃了纠结“变量名拼写、断言字眼对齐”这类琐碎的表层修补，而是聚焦于解决四大核心工程障碍：

### 1. 软件工程分层：交互入口与核心逻辑的彻底解耦

* **我遇到的问题**：测试执行慢，代码职责边界模糊。排查后发现，早期为了省事，把交互逻辑、自动化测试和底层调度混在了一起，导致测试与日常交互互相牵制。
* **我的思路**：**交互层（CLI/UI）只负责做输入输出与驱动，控制层（Controller）与核心内核（Kernel）绝不能对具体交互形式产生硬依赖。**
* **落地方案**：
* `main.py`：纯粹的 CLI 命令行交互，给无图形界面的服务器使用。
* `run_all_tests.py`：纯自动化评测入口，一条命令跑完“离线单元回归 + 真实 API 跨窗口强隔离断言”，零阻塞、即跑即退。



### 2. 安全沙箱防逃逸：AST 替代 `eval`

* **我遇到的问题**：`calculator` 需要支持复合运算（如 `500*0.8`），若直接调用 Python 的 `eval()`，不仅存在安全隐患，而且生产审计时无法过关。
* **我的思路**：禁止使用黑名单正则，改用 **AST（抽象语法树）白名单求值器**。
* **落地方案**：解析表达式语法树，白名单只放行 `BinOp`（加减乘除、幂、整除）、`UnaryOp` 和数值节点。一旦检测到任意模块导入、系统调用或函数调用，在解析期直接抛出 `ValueError`，从根源掐死代码逃逸可能。

### 3. 自愈闭环：截断 JSON 补齐与运行时自我纠偏

* **我遇到的问题**：真实大模型不可控。在长文本推理或网络微波动时，偶尔会输出截断的 JSON（缺少闭合 `}`），或直接不按规矩输出纯文本。
* **我的思路**：不能让调度器直接崩掉报错，要实现**前端语法补齐 + 后端语义自愈**的双重防线。
* **落地方案**：
* **尾部括号补齐**：解析层在 JSON 被截断时，按缺失的闭合花括号逐层补齐并重试解析（最多补 4 层），恢复“买牛奶”这类被截断的工具调用。
* **Feedback 纠错反哺**：若模型执意输出非 JSON 内容，Runtime 捕获 `parse_error`，将错误提示作为一轮 Observation 喂回上下文，驱动模型在下一轮自我校正。实测真实模型（`deepseek-v4-flash`）均能在第 2 轮 100% 纠正回标准格式。



### 4. 跨窗口会话与状态物理隔离

* **我遇到的问题**：在频繁切换不同会话（如 `user-a-window-1` 和 `user-a-window-2`）时，稍有不慎就会发生状态交叉污染。
* **我的思路**：在 SessionStore 层实现底层状态隔离，严禁使用模块级全局状态。
* **落地方案**：`Session` 对象独立维护各自的 `messages` 列表与 `working_memory` 字典。在跨窗口用例断言中严格验证：窗口 1 持续累加“带伞”、“买牛奶”，而窗口 2 仅保留“写周报”，两者的 Working Memory 处于强隔离状态。

## 三、 人机协同开发：我的 AI 使用方法论

在本次项目中，我深度结合了 **DeepSeek** 和 **Gemini** 两个大模型的不同特长，构建了一套高效的人机协作流程：

```
                    ┌────────────────────────┐
                    │      DeepSeek          │
                    │   - 核心逻辑快速原型    │
                    │   - 基础函数/算法草稿   │
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │       我 (架构师)      │
                    │   - 判定设计架构        │
                    │   - 设立单测 & 验收标准 │
                    │   - 把控系统整体演进方向│
                    └───────────┬────────────┘
                                │
                    ┌───────────▼────────────┐
                    │        Gemini          │
                    │   - 架构解耦与重构      │
                    │   - 协议一致性与排障    │
                    │   - 工业级测试体系建设  │
                    └────────────────────────┘

```

1. **前期（DeepSeek）：骨架搭设与算法草稿**
* 利用 DeepSeek 快速生成 AST 白名单算术解析、JSON 括号栈自愈的算法原型代码。
* 产出最初的 ReAct 循环逻辑草案。


2. **后期（Gemini）：架构拆解、协议一致性与边界加固**
* 当代码逐渐膨胀、职责边界模糊、返回契约与测试断言产生微小偏差时，引入 Gemini 进行顶层设计梳理。
* 确立了入口分工与自动化测试套件架构；规范了测试中对于 `current_todos` 的真实契约断言，确保系统既经得起严苛单测，又能在真实 API 评测中一键全绿。


3. **我的原则：业务契约为主，拒绝为迁就断言改动正确设计**
* 当测试报错时，我并没有盲目去改动已经写好的正确业务逻辑（例如将 `current_todos` 降级改回 `todos`），而是明确：**业务代码的实现契约是唯一的真理标准，测试必须忠实地反映业务设计**。通过指导 AI 修正过时的测试断言，最终达成了系统内部逻辑自洽。

### 4. 实际使用的开发 Prompt 摘录（可复现）

以下是本次开发中真实使用过的几条关键 Prompt（均针对本项目功能点，可直接复现）：

**① 骨架生成（给 DeepSeek）**
> 用 Python 从零实现一个最小 ReAct Agent，不依赖 langgraph 等任何框架。主循环：接收输入 → LLM 决策(直接回复 or 调工具) → 调工具 → 据工具结果决定继续循环 or 返回。工具用注册表管理（每个工具含 name/description/参数 JSON Schema），LLM 基于 Schema 自主决策。LLM 输出解析成 thinking / tool_call / final_answer 三种。只允许用 httpx 调 OpenAI-compatible API。

**② 安全求值（给 DeepSeek）**
> calculator 工具不要用 eval，用 ast 白名单实现：只允许数字、四则运算、括号、幂、取模，遇到 import / 属性访问 / 函数调用直接抛 ValueError。

**③ 容错解析（给 Gemini）**
> LLM 输出的 JSON 可能带 ```json 围栏、前后废话、被截断缺 }。写 parser：先正则抓 <thinking> 标签并剔除、再去围栏、再抠第一个 {...} 块；截断时补 } 逐层重试；arguments 可能是被双重序列化的字符串，要解包。

**④ 会话隔离（给 Gemini）**
> session 用 session_id 隔离，todo 状态存 session.working_memory（不放模块级全局变量），两个窗口互不影响；历史超长用 head-tail 压缩，中间折叠成摘要占位，且折叠消息用 user 角色避免连续 assistant。

**⑤ 边界审查（给 Gemini）**
> 站在面试官角度，列出这个 agent 最容易漏测 / 被追问的点，并补对应测试用例。

> 使用心得：**先给 AI 一个明确的、带约束的 prompt 让它产原型；再让 AI 站在"面试官/审稿人"视角挑刺；自己始终做"验收与裁决"的那一环——AI 负责生成，我负责判断对错和拍板设计。**

## 四、 真实 API 验收结论

全链路自动化测试套件（`python run_all_tests.py`）运行结果：

* **单元测试（Pytest，21 项全量通过）**：
* 覆盖 AST 沙箱拦截、除以零防御、截断 JSON 恢复、Working Memory 动态挂载、Head-Tail 安全压缩。


* **端到端真机验收（真实模型 API，6 阶段跨窗口全量通过）**：
* 阶段 1（窗口 1 复合指令与状态持久化）：成功查天气并记入“带伞”。
* 阶段 2（窗口 2 会话物理隔离）：记入“写周报”，断言窗口 2 未被窗口 1 污染。
* 阶段 3（切回窗口 1 状态累加与计算）：追加“买牛奶”，完成 `500*0.8` 预算代数运算，断言持久化正常。



该系统在保证极简代码体量的同时，展现出了高可用、强隔离、具备自我修复能力的工业级 Agent Harness 架构水准。
