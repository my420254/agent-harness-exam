## 模块一：Context / Performance（题 1）

**题：长窗口/多模态首 token 5-10s，如何低成本压到 2s？**

### 1. 根因定位
首 Token 延迟（TTFT, Time To First Token）核心由 **Prefill 阶段（对输入所有 Token 进行并行 KV 计算）+ 首次 Decode** 决定。在长窗口和多模态场景下，Prefill 属于重度 **计算受限（Compute-Bound）与带宽受限**，输入上下文越长、图片 Patch 展开的视觉 Token 越多，计算与显存加载耗时呈超线性增长。

### 2. 梯队式优化方案（按实施成本由低到高）
1. **跨轮次前缀缓存（Prefix Caching，收益最大、成本最低）**：
   - 将不变的 System Prompt、工具列表（JSON Schema）、乃至前序公共对话前缀严格对齐置顶。
   - 利用推理框架（vLLM 的 PagedAttention Prefix Caching、SGLang RadixAttention 或商业模型上下文缓存），复用已算好的 KV Cache，仅对增量 Query 进行 Prefill，可抹除 70%~90% 的 Prefill 耗时。
2. **多模态与上下文减枝（Token Pruning）**：
   - **多模态**：限制图片输入分辨率、采用动态分辨率分档（如 Qwen-VL 的动态分辨率、Gemini 的视觉 Token 合并）；对多图/视频仅提取关键帧；在边缘侧先做视觉 Token 压缩（提取简要视觉描述）替代原始多模态输入。
   - **长文本**：实施“头部任务保留 + 尾部活跃上下文 + 中间折叠压缩（Head-Tail Truncation）”策略；精简工具参数描述，剔除冗余字段。
3. **Chunked Prefill 与 Speculative Decoding（框架级优化）**：
   - 开启 Chunked Prefill，将长 Prefill 切片并发插槽执行，避免长请求阻塞并发批次。
   - 补充：Speculative Decoding 主要加速**后续 token（decode 阶段）**，对首 Token 帮助有限；首 Token 更直接的手段仍是 Chunked Prefill + Prefix Cache。
4. **模型分流与意图路由（Routing）**：
   - 入口前置轻量路由器（如 3B/7B 小模型或正则），普通短任务路由至轻量级模型，复杂多模态/超长分析任务才交由主力大模型。
5. **感知体验降延时（UX Masking）**：
   - 采用 SSE 流式推流；在建立连接的第 100ms 内先下发“正在检索/深度思考中”的状态指示块，掩盖物理 Prefill 耗时。

### 3. 权衡取舍
- **Prefix Caching vs. 动态 Prompt**：前缀缓存强依赖提示词结构稳定性，一旦动态内容（如当前时间、随机变量）插在最前面，缓存将全量击穿；因此必须坚持 **“静态前缀居前，动态状态置后”**。
- **综合策略**：**Prefix Cache 奠底 + 动态 Head-Tail 压缩减枝 + 流式状态反馈** 为生产级最优性价比解法。
- **自建推理的补充**：预算允许时，可叠加 KV Cache 量化（FP8/INT4）与 FlashAttention 类算子进一步压 Prefill 显存带宽；但优先级低于前缀缓存。

## 模块二：Memory（题 2）

**题：memory 经典框架是什么？发展趋势？头部玩家怎么做？**

### 1. 经典框架映射
借鉴认知心理学模型，工业级 Agent Memory 映射为四层体系：
- **工作记忆（Working Memory）**：当前正在执行的任务看板、临时变量、待办列表；映射为**当前轮次 System Prompt 动态挂载区**或图状态（Graph State）。
- **短期/情景记忆（Short-Term / Episodic Memory）**：最近 N 轮带时序的会话交互与工具执行日志；映射为**滑动窗口历史流**。
- **长期/语义记忆（Long-Term / Semantic Memory）**：长期跨会话沉淀的事实与偏好；映射为**向量数据库（Vector DB）或知识图谱（KG）**。
- **程序记忆（Procedural Memory）**：Agent 如何调度工具的 SOP 与技能库；映射为 **Few-Shot Examples / Prompt 规则模板**。

### 2. 发展趋势
1. **接口协议一等公民化**：记忆从散落的 RAG 脚本，演变为标准化协议插件（如 Anthropic 的 MCP Memory Server）。
2. **记忆双轨流转（Sleep-Time Consolidation）**：模拟人类睡眠归纳，在 Agent 空闲期异步执行抽取、去重、冲突消解与摘要下沉，避免阻塞在线推理；并把**反思/自我总结**（Reflexion 式）也作为记忆写回的一部分。
3. **召回范式升维**：由“纯向量相似度检索”转向 **“元数据过滤 + 关键词 BM25 + 向量密实检索 + 时间衰减因子 + 重要性打分 + 交叉编码重排（Rerank）”**，同时引入记忆冲突消解。
4. **实体关系网络（Entity Graphs）**：逐步引入轻量图结构追踪实体属性变化，解决纯向量检索导致的“前后偏好冲突”难题。

### 3. 头部玩家实践
- **Letta (原 MemGPT)**：操作系统级分层管理，率先将内存划分为 Core Memory、Recall Memory、Archival Memory，由 Agent 显式调用函数做换入换出。
- **Mem0 / Zep**：主打即插即用的多租户跨会话记忆服务，引入图谱融合与异步去重流水线。
- **OpenAI / Claude Built-in**：平台级隐式自省抽取，赋予终端用户完全透明的“增删改查”记忆控制面板。

## 模块三：Task（题 2）

**题：每天 9 点根据昨天聊天做复盘总结，怎么设计？**

### 1. 架构流水线设计
拆成 5 个阶段，每天 9 点由调度器触发：

1. **触发（Scheduler）**：平台级定时任务（cron / 消息队列延迟消息）触发，需保证**按用户时区（而非 UTC）**、幂等（重复触发不重复生成）。
2. **取数（Event Log Read）**：读取"昨天 0 点 ~ 今天 0 点"（用户本地时区）的对话事件日志（结构化事件：用户输入 / Agent 动作 / 工具结果 / 结论），而非聊天原文；对话量极大时用**增量抽取 + 已处理 checkpoint**，避免每天全量重跑。
3. **抽取与总结（LLM Summarize）**：LLM 从事件流中抽取"做了什么 / 关键决策 / 未完成事项 / 待办"，生成结构化复盘；多用户可批量，但要控制单次输入长度。
4. **写回记忆（Memory Write）**：复盘结果作为一条情景记忆写入长期存储（向量库或结构化表），并同时产出一份**可检索摘要 + 关键实体**，便于后续"我上周在干嘛"的召回。
5. **通知（Notify）**：推送给用户（IM / 邮件 / 飞书卡片）。

### 2. 关键设计权衡
- **数据源粒度**：太细（原始消息）成本高、噪声大；太粗（只存结论）复盘信息量不够 → 应在 Agent 运行时就把"值得记的事件"结构化落库。
- **可靠性**：失败重试 + 幂等 + 断点续跑；增量处理昨天新增事件，不重扫历史。
- **隐私边界**：按用户隔离，复盘内容绝不串号。

## 模块四：Tool / Session Runtime（题 2）

**题：session busy 时，用户又发新消息 / 异步工具完成事件到达，runtime 如何处理？**

### 1. 核心思路
用 **状态机 + 队列 + 单写者**，做到不丢、不覆盖、可恢复。

1. **session 状态机**：`idle → busy → waiting_async → idle`，状态落库（不依赖内存，进程重启不丢）。
2. **busy 时收到新用户消息**：入 `pending` 队列（排队），先给用户一个"稍后处理"的即时回执；不默认打断当前任务，但**高风险控制词（"停/取消/急停"）支持安全打断**。队列按到达顺序消费。
3. **异步工具完成事件**：更新任务状态 + 写结果；若 session 正处于 `waiting_async`，唤醒它继续 loop；若已被打断/超时，结果仍持久化，用户下次回来可查，并打上**"未读结果"标记或主动推送**。
4. **竞态处理**：每个 session 一个**单写者**（单机 worker 或 **Redis 锁 / session 级 lease**），事件串行处理；任务状态用"版本号/状态机"保证幂等——完成事件重复投递不重复执行。

### 2. 权衡
- **排队 vs 取消**：排队体验稳但可能堆积；取消干净但丢上下文 → 默认排队 + 支持显式取消。
- **事件推送 vs 轮询**：推送（SSE/回调）及时但要处理断线重连；轮询简单但有延迟。
- **结果落哪**：一定落持久化存储，内存只是缓存——否则进程一崩异步结果就没了。
- **可观测性**：事件流全程落 Trace（节点事件 + 版本号 + 耗时 + token），配 metrics；任何"排队/唤醒/打断"都能从 trace 定位，这是运行时设计的底线。

## 模块五：Agent Runtime 架构对比（题 1）

**题：Claude Code 的工具输出方式 vs 国内 GLM/豆包等 OpenAI-compatible function calling 有什么不同？优缺点？**

### 1. 本质区别
两者都是"工具调用进上下文"，差异在**工具结果的表示与回流方式**：

- **Claude Code**：工具是**原生 tool_use 文本块**（且也支持严格的 tool schema，并非完全自由文本），工具结果以 `user/tool_result` 文本块回填，和普通文本**同构地拼进上下文流**；工具结果可以很长（读文件、终端输出），模型在"文本 + 工具结果"的连续流里边读边继续决策。核心差异不在"有没有 schema"，而在**结果的回流方式更偏文本流**。
- **OpenAI-compatible function calling（GLM/豆包等）**：模型输出**结构化 `function_call(name, arguments)` JSON 字段**，框架执行后以 `role:"tool"` 消息回填，模型再生成下一轮。

### 2. 各自优缺点
| | Claude Code（文本块） | function calling（结构化消息） |
|---|---|---|
| 工具结果表示 | 大段文本进上下文 | 结构化 JSON 回填 |
| 优点 | 结果可被模型"逐字阅读"、自由引用；适合长文本工具（读代码/终端）；工具常驻（MCP server） | 机器可解析，易做参数校验、并行调用、自动重试；token 更省 |
| 缺点 | token 消耗大、上下文膨胀快；结果过长易淹没关键信息 | 结果脱离文本流，模型理解依赖框架正确回填；多工具嵌套不够自由 |

### 3. 设计动机与落地
- Claude Code 面向"写代码/改文件"——工具结果本身就是大量文本、需要模型细读；
- function calling 面向"工具结果是结构化小对象、需要稳定可解析"；
- 本题代码落地：用"文本 + JSON 动作 + 工具结果回填"，取 function calling 的结构化可解析，同时把工具结果作为消息回填进上下文，兼顾两者且不依赖任何框架。
