# 架构设计题答案（5 模块各 1 题）

> 原则：写方案 + 权衡 + 为什么，而不是堆字数。

## 模块一：Context / Performance（题 1）

**题：长窗口/多模态首 token 5-10s，如何低成本压到 2s？**

先定位根因：first token 延迟 ≈ **prefill（把整段输入过一遍算 KV）+ 第一个 token 的 decode**。长窗口/多模态输入 token 多，prefill 是 compute-bound，所以慢。

按成本从低到高：

1. **前缀缓存（最有效、成本最低）**：system prompt、工具清单、历史消息里"不变的前缀"这部分 KV 直接复用，只 prefill 增量部分。vLLM `enable_prefix_caching`、DeepSeek 的 context caching 都天然支持，首 token 能砍掉一大半。这是首选。
2. **减输入 token**：工具 Schema 精简、历史只放"最近 N 轮 + 摘要"、多模态图先降采样/缩略图、只送关键帧。token 少了 prefill 自然快。
3. **预热 + 常驻**：空闲时把 system prompt 预填一次并缓存，用户一来就是热缓存。
4. **模型分流**：简单任务走小模型（7B/9B），只有真正长窗口任务才上大模型。
5. **UX 层面的"快"**：SSE 流式 + 先推一个"正在思考"占位 token，把感知延迟压下来（不改变真实首 token，但体验好）。

权衡：前缀缓存命中率依赖输入稳定（历史变化越大命中越低，所以"固定前缀 + 增量历史"很关键）；减 token 有信息损失风险；分流有不一致风险。**正确组合 = 前缀缓存打底 + 减输入 + 流式占位。**

## 模块二：Memory（题 2）

**题：memory 经典框架是什么？发展趋势？头部玩家怎么做？**

经典框架来自认知科学的三分：**工作记忆（working）+ 短期记忆（short-term）+ 长期记忆（long-term）**，再加**情景记忆（episodic，发生过什么）和语义记忆（semantic，学到了什么）**。工程映射：

- 工作记忆 = 当前对话窗口 / 图状态；
- 短期 = 最近会话 + 结构化状态（待办、任务进度）；
- 长期 = 向量库 / 结构化存储，靠检索召回；
- 情景 = 事件日志的摘要抽取。

发展趋势：
1. **记忆从"附加功能"变成"一等公民"**，标准化成 MCP memory server（Anthropic 推的 MCP 就有 memory 接口）；
2. **分层 + 自动搬运**：重要信息从短期自动沉淀到长期，不是全量堆；
3. **召回从纯向量走向混合**：向量 + 关键词 + 元数据过滤 + 时间衰减 + 重排；
4. **记忆整理（sleep-time consolidation）**：空闲时对记忆做合并、去重、冲突消解。

头部玩家：
- **Letta / MemGPT**：最早把"内存管理"当核心——分层记忆 + 显式的记忆读写与整理，是方法论标杆；
- **OpenAI / Claude 的 built-in memory**：把记忆做成产品层能力，用户可管理；
- **Mem0 / LangMem / Zep**：把记忆做成可插拔服务，主打"跨 session 持久 + 检索"。

趋势本质：**记忆的问题不是"存"，而是"何时写、写什么、怎么召回、怎么遗忘"。**

## 模块三：Task（题 2）

**题：每天 9 点根据昨天聊天做复盘总结，怎么设计？**

拆成 5 件事：

1. **触发**：平台调度器（cron / 消息队列延迟任务）每天 9 点触发；注意时区、幂等（同一任务重复触发不重复生成）。
2. **取数**：读"昨天的对话事件日志"（按用户/会话过滤，时间窗口 `[昨天 0 点, 今天 0 点]`）。这里的关键是**数据源是结构化事件，不是聊天原文**——日志里已记录了用户输入、agent 动作、工具结果、结论。
3. **抽取 + 总结**：LLM 从事件里抽"做了什么 / 关键决定 / 未完成事项 / 待办"，生成复盘。多用户可批量，但要控制单次输入长度。
4. **写回记忆**：复盘结果作为一条"情景记忆"写入长期存储（向量库或结构化表），供以后"我上周在干嘛"这类问题召回。
5. **通知**：推送给用户（IM/邮件）。

关键设计点：
- **可靠性**：任务失败重试、幂等、断点续跑；
- **增量 vs 全量**：只处理昨天新增事件，不重扫历史；
- **隐私/边界**：按用户隔离，复盘内容不串号。

权衡：定时任务天然是"准实时即可"，不需要秒级；难点在**事件日志的粒度**——太细（原始消息）成本高，太粗（只存结论）复盘信息量不够，所以要在 agent 运行时就把"值得记的事件"结构化落库。

## 模块四：Tool / Session Runtime（题 2）

**题：session busy 时，用户又发消息 / 异步工具完成事件到达，怎么处理？**

核心思路：**用状态机 + 队列，做到不丢、不覆盖、可恢复。**

1. **session 状态机**：`idle → busy → waiting_async → idle`，状态落库（不依赖内存，进程重启不丢）。
2. **busy 时收到新用户消息**：入 `pending` 队列（排队），给用户一个"稍后处理"的即时回执；不推荐直接中断当前任务（除非是高风险/可安全打断）。队列按到达顺序消费。
3. **异步工具完成事件**：事件到达时更新任务状态 + 写结果；若 session 处于 `waiting_async`，则唤醒它继续 loop；若 session 已被打断/超时，结果仍持久化，等用户下次回来能查到。
4. **竞态处理**：每个 session 一个**单写者**（一个 worker 或一把分布式锁），事件串行处理；任务状态用"版本号/状态机"保证幂等——完成事件重复投递不重复执行。

权衡：
- **排队 vs 取消**：排队体验稳但可能堆积；取消干净但丢上下文。默认排队 + 可显式取消。
- **事件推送 vs 轮询**：推送（SSE/回调）及时但要处理断线重连；轮询简单但有延迟。
- **结果放哪**：结果一定落持久化存储，内存只是缓存——否则进程一崩异步结果就没了。

## 模块五：Agent Runtime 架构对比（题 1）

**题：Claude Code 工具输出 vs OpenAI-compatible function calling 的区别与各自优缺点？**

两者本质都是"工具调用进上下文"，区别在**工具结果的表示与回流方式**：

- **Claude Code**：工具是**原生 tool_use 文本块**，工具结果以 `user/tool_result` 文本块回填，**和普通文本同构地拼进上下文流**。特点是工具结果可以很长（读文件、终端输出），模型在"文本 + 工具结果"的连续流里边读边继续决策。
- **function calling**：模型输出**结构化的 `function_call(name, arguments)` JSON 字段**，框架执行后以 `role:"tool"` 消息回填，模型再生成下一轮。

各自的优缺点：

| | Claude Code（文本块） | function calling（结构化消息） |
|---|---|---|
| 工具结果表示 | 大段文本进上下文 | 结构化 JSON 回填 |
| 优点 | 结果可被模型"逐字阅读"、自由引用；适合长文本工具（读代码/终端）；工具常驻（MCP server） | 机器可解析，易做参数校验、并行调用、自动重试；token 更省 |
| 缺点 | token 消耗大、上下文膨胀快；结果过长易淹没关键信息 | 结果脱离文本流，模型对结果的理解依赖框架正确回填；多工具嵌套不够自由 |

设计动机：Claude Code 面向"写代码/改文件"这种**工具结果本身就是大量文本、需要模型细读**的场景；function calling 面向**工具结果是结构化小对象、需要稳定可解析**的场景。

我的落地选择（本题代码里）：用"文本 + JSON 动作 + 工具结果回填"——取 function calling 的结构化可解析，同时把工具结果作为消息回填进上下文，兼顾两者，且不依赖任何框架。
